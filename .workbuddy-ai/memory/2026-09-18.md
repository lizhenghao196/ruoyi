**哪天拦截器改成 `??` 就会把成功当失败。** 所以调用处一律不判 `code`，只判 `data` 里有没有 `nodeFinishedSms`。

### 几个刻意的设计决定（都有理由，别随手改）

1. **先查后开，不是先开后填**。`openSmsSetting` 里 `await getPlanExtraInfo` 成功后才 `visible: true`；
   查失败**不开弹窗**只弹错误提示。

   而且拿不到当前状态就开弹窗，用户一确定就把一个来源不明的值写了回去。
   → 所以这个弹窗**没有 loading**（`querying` 驱动的是按钮置灰，不是弹窗遮罩）。

5. **提交成功后不在本地假装已生效**：接口 `data` 是 null，拿不到落库后的真值；
   直接关弹窗，下次打开重新查 —— 那时看到的就是后端真实的持久化结果，
   「设置成功但其实没生效」只有这样才看得出来。
6. 开关图标**不加 `is-spin`**：`is-spin` 是刷新按钮的语汇（转圈箭头），铃铛转圈很怪。只置灰。

## 13:00 新增「右键节点 → 暂停 / 取消 / 恢复」三个节点操作

### 需求

用户给了三张截图（参考实现），三个动作共用一个接口：
`POST /release/executeIndex/updateNodeStatus` + `{ aniInstanceNodeId, operation }`，
`operation` ∈ `STOP`（暂停）/ `CANCELLED`（取消节点）/ `RECOVER`（恢复）。

**用户额外提的关键点：请求成功后要重置定时器** —— 立刻重新拉数据、开启新定时器。
理由：「立刻看到新状态」比「等 3s 内的旧定时器下一次触发」更自然，
而且旧定时器可能在下一次（< 3s 内）跟新数据并发触发，节点卡片会有节奏不齐的闪烁。
所以链路是：**stopPolling → fetchAll(silent) → startPolling**。

### 现状

`nodeMenu.js` 已经把 `stopIt / recover / cancelIt` 三个动作的菜单可见性按 `aniStatus`
配好了（RUNNING 有 stopIt、STOP 有 recover、INIT 两个都有、SUCCESS/FAILED/CANCELLED 无）。
但页面里 `actNodeStop / actNodeCancel / actNodeRecover` 是 stub，只弹「接口待接入」提示。

1. **新事件 `refresh-with-loading` 而不是改 `refresh`**。
   `refresh` 走 `reloadDetailAtoms`（默认不切 loading，刻意避免闪遮罩 —— 注释里写过原因）。
   批量跳过用户**明确要** loading，所以另开一条事件 + 一个 `{ withLoading: true }` 选项。
   两条路径行为**完全互不干扰**：原子级确认/跳过仍是「无感刷新」，批量跳过是「带 loading 刷新」。
   改原 `refresh` 会让所有原有调用方一起闪遮罩，那是回归。
2. **覆盖表机制复用 `patchFuncStatus`**。与 `updateFunctionStatus` 完全同构 —— 改原始 `aaiInstanceFunctionName` 字段

5. **`functionSelList` 去重按 funcName**：合批场景下多个原子可能带同名函数，跳两次没意义。

   同名时归属**先到先得**（先遍历到的原子）。
6. **接口入参里两个开关转 `'Y'/'N'`**：组件不认线上协议，翻译在组件里做（与 `SmsSettingDialog` 同套路）。

## 15:40 「函数批量跳过」第 6 轮：flex-grow 强制拉伸导致 select 之间大空白

### 用户反馈

用户自己改了一下，发现 `flex: 1 1 220px;` 去掉就好了，问**为啥加了这个**。
截图也显示 select 之间间隔过大（不是简单的 spacing）。

### 根因（我自己加错了）

我加 `flex: 1 1 220px` 的初衷是「让两个 select 平分剩余空间显得整齐」：

- `flex-grow: 1` → 让两个 select **强制拉伸**填满容器剩余空间
- `flex-basis: 220px` → 基准 220px
- `min-width: 220px` → 最小 220px

60% 弹窗下，container ~676px，switch 140px 固定 + margin 8px，
剩余 = 676 - 140 - 8 = **528px**，atom/fn 各 `flex-grow: 1` → 各占 **260px**。

260px 对 select 是「**远超内容需要**」（placeholder 才 120px），所以两边 select 看着
中间一大块空白，**感觉「间隔太大」**。

### 用户验证的方向就是正确的

去掉 `flex: 1 1 220px` 后：

- form-item 默认 `flex: 0 1 auto`（不拉伸）
- form-item 宽度由内容决定：label 72px + select（~120px）≈ 192px
- 两个 select 列总和 ~384px，加 switch 140px + margin = 540px
- 富余 136px 富余在右侧（看着留白均匀、不挤压）

### 修法

```scss
&__atom {
  // 移除 flex: 1 1 220px；用默认 flex: 0 1 auto
  min-width: 200px; // 只兜底防太窄
}
&__fn {
  min-width: 200px;
}
```

`min-width` 还在，但**不放 `flex-grow: 1`**：select 这种由内容决定宽度的控件，
**默认 flex 就行**，硬拉伸只会把布局撑大。

### 这次的反思（更通用）

`flex-grow: 1` 看起来「让布局整齐」，但**用拉伸填空白**会撑大 select 之间的视觉间隔。

**判断要不要加 `flex-grow: 1` 的简单规则**：

- ✅ 该列**确实应该平分剩余空间**（如侧边栏 + 主内容区，比例固定）→ 加
- ❌ 该列**宽度跟着内容走**（select / input / switch / 文字）→ **不加**，用默认

具体到这个项目：

- inline form 里 select 列默认 `flex: 0 1 auto`（自然内容宽度），看着紧凑
- 想要 select 列**变宽**应该用 `width` 显式给，而不是 `flex-grow`
- 想要 form-item **不被挤压**用 `min-width` 兜底，**不是 flex-grow**

→ 下一回写 el-form inline 多列布局，**多列默认不加 flex-grow**，只在确实要"平分剩余"时才加。

## 「查看明细」弹窗：自动刷新（刷新 / 停止刷新 + 定时器）

用户要求：在「一键跳过失败函数」右边加一个刷新按钮，点开定时器刷明细；
按钮变「停止刷新」，右侧加「刷新中...」黄色呼吸文字；刷新时弹窗要 loading；
展开的行刷新后仍展开；关弹窗要停定时器（注意销毁）。

### 定时器放哪：**放页面，不放弹窗**

弹窗是哑组件（不自己调接口、不本地改 atoms），而且「关弹窗」只有 `closeDetail()` 一条路 ——
定时器跟着数据所有权走，销毁点才唯一。弹窗只 `$emit('toggle-auto-refresh')` + 用 prop
`autoRefreshing` 显示文案，**自己不存状态**（否则会出现「弹窗以为在刷、页面其实停了」）。

- 常量 `DETAIL_POLL_INTERVAL = 3000`（与页面轮询同频，两边状态不会打架）
- data：`detailAutoRefresh`（开关）/ `detailTimer`（句柄）/ `detailRefreshing`（防堆叠）
- 三个销毁点（缺一个都会漏出后台定时器）：
  1. `closeDetail()` —— **放在 `if (!this.detail.visible) return` 之前**，否则「本来就没开」的关闭路径会漏
  2. `beforeDestroy()` —— 切路由 / 关标签页
  3. `refreshDetailTick()` 里「弹窗已关 → 兜底停表」
- `startDetailAutoRefresh()`：开头先判 `detail.visible`（防僵尸定时器）+ 先 `stop()` +
  **立刻刷一次**再挂 interval（点了马上有反馈，不用干等 3s）
- `stopDetailAutoRefresh()`：**不动 `detailRefreshing`** —— 它的语义是「有一拍正在飞」，
  由那一拍自己的 finally 复位；在这里置 false 会让「停→立刻再开」的守卫形同虚设
- tick 走 `reloadDetailAtoms({ withLoading: true })`（用户要求刷新时 loading）

### 刷新后保持展开（`reapplyExpand`）

`expand-row-keys` 在 Element 里是**非 deep 的 prop watcher**，数组引用不变就不触发；
数据整体换掉后能不能保持展开，取决于 `updateExpandRows` 按 rowKey 重映射 —— 那是实现细节、不是契约。
所以 `watch.atoms` 里显式 `reapplyExpand()`：`this.expandRowKeys = this.expandRowKeys.slice()`
