## 需求：变更编排 —— 工单原子所在环境/流加角标

### 需求背景
右侧工单面板选中某工单后，属于该工单的原子会分布在若干环境/流/节点上。原来只靠 `is-match`（描边+浅底）和 `is-dim`（降透明度）区分，选中态实心填充时命中标识几乎被吞掉，不够明显。用户要求在环境 / 流的**右上角加一个小图标**，表示"这里含有该工单的原子"。

### 改动（纯前端，未动数据结构和接口）
- `components/EnvFlowBar.vue`：
  - 环境 chip 加 `position: relative`，与流 chip 保持一致。
  - 环境 chip、流 chip 内在 `matchOf(...)` 命中时渲染 `.match-mark` 角标（右上角，`svg-icon icon-class="component"`，title 说明原子数量）。
  - `.match-mark`：15×15、主题色实底、白字、`border-bottom-left-radius` 切角；选中态改白底+主题色图标以免和实心填充糊在一起；`pointer-events: none` 不挡点击。
  - 命中态 `is-match:not(.is-active)` 补 `box-shadow` 环 + 名称变主题色；未命中态 `is-dim` 透明度从 0.5 提到 0.62 并加极浅底色，避免命中/未命中难分辨。
- `components/FlowCanvas.vue`：流程节点同样加 `.match-mark`（16×16，切角 9px），与上方栏视觉统一。

### 关键实现点（复用）
- 命中判定统一走 `matchOf(map, key)`：环境用 `envMatches[envKey]`、流用 `flowMatches[flowId]`、节点用 `nodeMatches[flowId + '#' + nodeId]`（节点 id 只在流内唯一）。
- 角标图标准确可用的是 `component.svg`（列表里没有 "atom"）。
- 改完前端无需构建，dev server 热更新即可，已验证编译通过。

### 返工（用户反馈"太丑"，第一版右上角角标被否）

第二版方案（最终采用）：
- **彻底删掉 `.match-mark` 角标**（EnvFlowBar 和 FlowCanvas 都删干净）。
- 命中态改为**左侧主题色竖条**（`&.is-match::before`，宽 3px、上下内缩、右侧 2px 小圆角），环境 chip 和流 chip 均适用；流 chip 竖条 bottom 缩 11px 给底部进度条让位，并加 `z-index:1`。
- 环境 chip 补 `position: relative`；流 chip 本来就有。
- 未命中态 `is-dim:not(.is-active)` 透明度统一 0.45 且去掉多余底色，hover 时恢复 1 —— 与 FlowCanvas 节点的 0.45 对齐，一致性更好。
- 删掉原「选中态实心填充」的命中覆盖规则（`.is-match:not(.is-active)` 那套已不需要）。
- **`.is-active` 的实心主题色填充规则已在本次被整体移除**（env-chip / flow-chip 均是），选中态现在靠 `:hover` 的同款描边表达。若用户后续觉得"选不中"，需重新加回选中态区分。
- FlowCanvas 节点同步：命中只保留左侧竖条 + 描边，去掉渐变底和 box-shadow；未命中 0.45；新增 `&.is-active { opacity: 1 }` 保证选中节点不被弱化。
- 注意：EnvFlowBar 的 `.chip-badge`（计数胶囊）是原有元素，第二版保留复用，未新增。

### 第三版（最终定稿，用户明确指定方案）
用户直接给了方案，两点要求：① 含该工单的项（环境、流）**边框改成流光模式**；② 选中态**给项加背景色**；③ 去掉流项下面的**小横条**。

实现：
- **删除流项底部进度条** `flow-chip__bar`（就是用户说的小横条），模板 + 样式全删；连带清理了因此不再使用的 `flowProgress()` 方法；flow-chip 的 `padding` 从 `0 12px 3px` 改回 `0 12px`。
- **边框流光**（env-chip / flow-chip / flow-node 三处统一）：
  ```scss
  &.is-match {
    border-color: transparent;
    &::before {
      content: ''; position: absolute; inset: 0; z-index: -1; padding: 1px;
      border-radius: <同元素圆角>;
      background: linear-gradient(115deg, rgba(64,158,255,.25) 0%, rgba(64,158,255,.25) 35%, #409eff 50%, rgba(64,158,255,.25) 65%, rgba(64,158,255,.25) 100%) no-repeat;
      background-size: 260% 100%;
      -webkit-mask: linear-gradient(#000 0 0) content-box, linear-gradient(#000 0 0);
      -webkit-mask-composite: xor;
      mask: ...; mask-composite: exclude;
      animation: chip-flow 2.6s linear infinite;
      pointer-events: none;
    }
  }
  @keyframes chip-flow { from { background-position: 200% 0 } to { background-position: -60% 0 } }
  ```
  关键点：靠 mask 的 content-box / border-box 异或只保留 1px 描边；元素需要 `position: relative` + `isolation: isolate` + `z-index: 0`，`::before` 用 `z-index: -1` 才不会盖住内容。
- **选中态改为加背景色**：`.is-active { background: var(--orch-accent-soft) }` + 名称变主题色，不再用实心填充。
- **未命中态**保持 `opacity: 0.45`，hover 恢复 1。
- FlowCanvas 的 `.is-active` 保留 `opacity: 1` 防弱化。

### 需求：变更编排 —— 工单原子所在环境/流标识（共 4 轮迭代）
本轮共改 4 次：角标 → 左侧竖条 → 单向流光边框 → 旋转流光+光晕。教训：
- 用户要"明显"但不要"突兀"，沿边界的动效比实体色块合适。
- 单向 `background-position` 位移在细长元素上**几乎看不出来**（渐变带太窄、移动太快掠过）。要"明显/花哨"应改用旋转 conic-gradient + 外发光。

### 第四版（流光加强，最终）
用户反馈"流光效果不明显，可以花哨一点"。改动（EnvFlowBar 的 env-chip / flow-chip + FlowCanvas 的 flow-node 三处统一）：
- 单向 linear-gradient 平移 → **旋转 conic-gradient 描边**：光带原地绕边框转圈（`from var(--flow-angle)`）。
  ```scss
  @property --flow-angle { syntax: '<angle>'; initial-value: 0deg; inherits: false; }
  @keyframes chip-spin { from { --flow-angle: 0deg } to { --flow-angle: 360deg } }
  ```
  用 `@property` 注册角度才能让 conic-gradient 平滑转动（否则自定义属性不参与插值，动画会跳）。元素加 `animation: chip-spin 2.4s linear infinite`。
- 描边宽度 `1px → 2px`，光带配色加大对比：底色 `rgba(64,158,255,.18)`，亮部依次 `#a5d5ff → #ffffff(292deg) → #409eff(320deg) → #7cc0ff`，形成"白热+蓝光"的扫光。
- **新增 `::after` 外发光层**：`filter: blur(6px)` + 蓝渐变，`opacity .55↔.95` 呼吸（`@keyframes chip-glow`），流光溢出到元素外围，是"明显"的主要来源。
- 层级：`::before` 为 `z-index:-1`（描边），`::after` 为 `z-index:-2`（光晕）。伪元素都用 `position:absolute; inset:0`（after 用 `inset:-1px`）+ `border-radius` 匹配父元素（chip 8px→9px、node 10px→11px）。
- 命中时同步强调文案/圆点：env 的 `__dot` 加 `box-shadow` 光环、`__name` 变主题色；flow 的 `__name` 变主题色；node 的 `atom-count` 变深。
- 旧 `chip-flow`（background-position 版）keyframes 已删除，两个文件各自保留 `chip-spin` / `chip-glow`（scoped 样式不共享，需重复定义；`@property` 也各写一份）。
- 待验证：`@property` 在 Chrome/Edge 支持良好；若不支持则退化为静态渐变+光晕呼吸（仍比之前明显）。

### 第五版（选中态定稿：方案 B）
用户要求先出方案再实施，对比了 4 个方案（A 淡底+左条 / B 描边加粗+外环 / C 实心填充 / D 深底+左条），**选定方案 B**。

**核心设计原则（本轮最重要的结论）**：「含该工单」已经占用了**边框通道**，所以选中态必须走**另一条通道**，否则两者必然打架 —— 这是前几轮反复翻车的根因。方案 B 用"描边加粗+外环"，视觉上属于"圈层"而非"填充面"，因此能与流光的旋转动画**共存**（实心填充会直接吞掉流光）。

三态梯度（env-chip / flow-chip / flow-node 三处统一）：
| 状态 | 表达 |
|---|---|
| 默认 | 1px `--orch-border` 灰边 + 白底 |
| hover | 1px `#a5c9f5` 浅蓝边（**刻意做弱**，不与选中混淆） |
| 选中 | 2px `--orch-accent` 主题边 + `0 0 0 3px var(--orch-accent-soft)` 外环 + 名称变主题色 |
| 选中+命中 | 上面全部 + 流光继续转（`box-shadow` 置 none，让位给 `::after` 光晕） |

实现要点：
- **padding 补偿**：边框 1px→2px 会让内容位移 1px，故 `.is-active` 里同步调 padding（env-chip `0 12px → 0 11px`；flow-chip 同；flow-node `11px 12px 10px → 10px 11px 9px`）。
- **环厚度联动**：`.is-match::before` 的 `padding` 默认 `1px`（对应 1px 边框），在 `.is-active.is-match` 里改为 `2px`（对应 2px 边框），保证流光带精确填满边框区域、不溢出。
- 移除旧的 `.is-active { background: var(--orch-accent-soft) }` 淡底方案（那是方案 A）。
- `&.is-active.is-match` 必须写在 `&.is-match` **之后**才能靠同权重+后置取胜；两个 chip 类和 node 类都遵守此顺序。
- 命中时圆点强调保留：env `__dot` 加光环、name 变主题色。

仍建议：`EnvFlowBar.vue` 与 `FlowCanvas.vue` 各存一份重复的 `chip-spin`/`chip-glow`/`@property`（scoped 样式不共享）。后续若要再加动画，可考虑抽到公共 scss（如 `_panel.scss`）统一维护。

### 第六版（色相分离，当前最终版）
用户反馈方案 B "还是不明显"，改为**用颜色区分两种选中情况**：
- **含该工单（选中）→ 金色流光**：`#f59e0b` / `#fbbf24` / `#fcd34d` / 高光 `#fffbeb`，光晕 `rgba(245,158,11,.55)→rgba(252,211,77,.32)`、`blur(7px)`、`opacity .85`；文字/圆点转 `#b45309`（amber-800，保证浅底可读）。
- **不含该工单（选中）→ 蓝色描边**：沿用 `--orch-accent` 2px + `--orch-accent-soft` 外环。
- 新增规则 `.is-active.is-match { border-color: transparent; box-shadow: none; &::before { padding: 2px } }`，让"选中+命中"时彻底走金色流光、不留蓝色残影。
- FlowCanvas 图例文案改为「含所选工单（金色流光）」，图例圆点同步改金色。

配色选型说明：蓝色是系统主色（`--orch-accent`，也可能是 `--current-color` 主题变量），金色作为**语义色**出现不冲突；蓝/金是对比明确的互补区间，比"同色系深浅"的区分度高得多。这也符合 `_panel.scss` 之外页面里已有的 amber 用法（order-tag `is-warning` 用 `#b45309`）。

经验总结（重要）：
1. **同色系内做区分（深浅/粗细）在密集 UI 里区分度不足** —— 用户连续 3 轮说"不明显"。要拉开，最有效的是**换色相**。
2. 预留"边框通道"给动画、用"圈层/填充"通道表达选中，这个分层是对的，应保留。
3. 后续若加第三种状态，建议继续沿"色相语义"扩展（如红=失败/阻断），不要回到同色深浅。
