## 执行界面简版：环境圆点汇总 + 画布自动滚动（14:3x）

**用户要求**（两条）：
1. 流里的状态要在环境小方块里也体现出来（现在只有流的小方块有）
2. 滚动条自动跟着「执行中」的节点走、把它放视野中间；节点报错就停在报错处；
   用户 20s 没滑滚动条才恢复自动滚动；操作弹窗开着时不自动滚动

**动手前先问了用户**（`AskUserQuestion`，因为原话自相矛盾：既说「流的小方块里也体现」又说「现在流的小方块状态体现出来了」，
但代码里流 chip 只有圆点+流名、没有节点色条）。用户选择：
- 环境 chip → **只改圆点**（按该环境下所有节点汇总配色），不加分布色条
- 流 chip → **保持现状**（仍取 `awiWorkflowStatus`）

### 关键判断（写进 REF §3.5 / §3.6 了）

1. **区分「用户滚的」和「程序滚的」只看输入事件，不看 `scroll` 事件**。
   画布**刻意不监听 `scroll`** —— 轮询每 3s 刷内容，按 scroll 记的话程序化滚动和「内容变短夹 scrollTop」
   都会被误判成「用户刚滚过」，自动滚动永远冻着不动（且不报错，只是「功能像没做」）。
   改成只认 `@wheel` / `@touchmove` / `@keydown`（只认滚动键）/ `@mousedown`（判是否点在滚动条上）。
   因此 `autoScrollBusy` 这类标志位是多余的，写完自己删掉了。
2. **`bad > run > confirm > stop` 天然实现「停在报错处」**：报错 / 待确认 / 挂起三档都不会自己消失 →
   目标一直是那个节点 → 位置差 < 6px → 不滚。
   用户先只要了「执行中 + 报错」，看完回复后追加要求把**待确认和挂起**也加进来（14:40）。
   这四档顺序**刻意和 `flowLayout.js` 的 `AGG_TONE_PRIORITY` 保持一致** ——
   这样「环境 chip 圆点什么颜色」和「画布居中哪个节点」永远指向同一件事，不会互相打脸；
   `esp_verify.mjs` [I] 段加了交叉断言，改一处不改另一处会红。
   真实 mock 数据里**没有 confirm / stop 节点**（21 条流全 0），所以这次改动在 demo 上看不出差别。
3. 换环境 / 换流要**先清零 `lastUserScrollAt`** 再滚 —— 用户主动换视野，不该被上一条滚动记录压住。
4. `.flow-graph` 顶边坐标要用 `getBoundingClientRect` 差值换算，**不能拿 `offsetTop`**（画布有 padding，offsetParent 不确定）。
5. 用真实 mock 数据实测：11 个环境里 **2 个**圆点颜色会变（`计划=SUCCESS` 但节点是 2 SUCCESS + 2 INIT → 蓝），
   正是这次要修的「圆点骗人」场景。
