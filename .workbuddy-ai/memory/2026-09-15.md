## 定位到真正的问题（关键！）

用户补充说明后，根因终于清晰：

> 「当环境和流包含工单时，再选中这个工单，和普通的仅包含工单的样式没什么区别。未包含的选中状态能看出来，但是包含工单的选中状态根本看不出来。」

**根因**：方案 B 里 `.is-active.is-match` 只做了两件事 —— `box-shadow: none`（撤掉蓝色外环，因为 `is-match` 已把 border 设为 transparent）+ `::before { padding: 1px → 2px }`（流光环加厚 1px）。

也就是说：**"仅含工单（未选中）"和"含工单 + 选中"的视觉差异只有 1px 的环厚度** —— 在 30px 高的 chip 上肉眼根本不可辨。这就是"看不出来"的真正原因。前几轮一直在调"命中 vs 未命中"的对比，却漏掉了"命中未选中 vs 命中已选中"这一对。

## 第七版（正解）：选中 + 命中 → 流光转金色

改动（`EnvFlowBar.vue` 的 env-chip / flow-chip + `FlowCanvas.vue` 的 flow-node，三处统一）：
- **`.is-match`（未选中）保持蓝色流光**不变 —— 表示"含该工单"。
- **`.is-active`（不含工单 + 选中）保持蓝色描边 + 外环**不变。
- **`.is-active.is-match`（含工单 + 选中）→ 流光整体转金色**：
  ```scss
  &.is-active.is-match {
    border-color: transparent;
    box-shadow: none;
    &::before {
      padding: 2px;
      background: conic-gradient(from var(--flow-angle, 0deg),
        rgba(245,158,11,.25) 0deg, rgba(245,158,11,.25) 190deg,
        #fcd34d 255deg, #fffbeb 288deg, #f59e0b 320deg, #fbbf24 345deg,
        rgba(245,158,11,.25) 360deg);
    }
    &::after {  // 光晕也转金，并加强
      background: linear-gradient(120deg, rgba(245,158,11,.6), rgba(252,211,77,.35));
      filter: blur(8px); opacity: .9;
    }
    .xxx__name { color: #b45309; }
  }
  ```
- 命中态的文字/圆点：仅"选中+命中"时才转金（`#b45309`），未选中命中仍是主题蓝。

**为什么这次能生效**：靠的是**色相切换**而非粗细微调。优先级上 `.is-active.is-match`（3 个类）> `.is-match`（2 个类），所以 `::before`/`::after` 的金色能稳定覆盖蓝色。

最终四态，两两差异都很大：
| 状态 | 表现 |
|---|---|
| 默认（不含工单，未选中） | 1px 灰边 + 白底 |
| 仅含工单（未选中） | **蓝色**流光 + 蓝色光晕 |
| 不含工单 + 选中 | 2px 蓝边 + 浅蓝外环 |
| **含工单 + 选中** | **金色**流光 + 金色光晕 + 文字转金 |

### 经验（很重要，后续复用）
- **要区分 N 个状态，优先用"色相"而不是"同一色系的深浅/粗细"**。同色系的细微差异在密集小尺寸 UI 里等于没有。
- 做状态对比时，要穷举**所有组合**（本例是 2×2 = 4 态），不能只看"命中 vs 未命中"这一对。前六轮反复失败的根源就是漏了"命中未选中 vs 命中已选中"。
- `.is-active.is-match` 这类组合选择器必须写在单状态规则**之后**，靠同源顺序 + 更高权重取胜。
